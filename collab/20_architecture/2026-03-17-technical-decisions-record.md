## 1. 数据库设计决策

### 决策编号: DB-001
#### 决策主题
checkins 表唯一约束策略选择

#### 决策时间
2026-03-17

#### 决策状态
✅ 已确定

#### 参与方
- 提议方: Backend Agent D012
- 决策方: 架构指导Agent D017
- 影响方: Backend, App, 业务产品

#### 问题背景
checkins 表需要防止用户重复打卡，但需要平衡业务灵活性和数据一致性。当前精确到秒的唯一约束可能导致合法重复打卡被拒绝。

#### 备选方案
##### 方案A: 按小时去重约束
- **描述**: `UNIQUE (user_id, poi_id, date_trunc('hour', checkin_time))`
- **优点**: 与业务冷却期（3600秒）对齐，允许用户离开后重新打卡
- **缺点**: 同一小时内无法重复打卡，可能影响测试场景
- **风险评估**: 低，可通过测试用户特殊处理

##### 方案B: 冷却期应用层控制
- **描述**: 数据库无唯一约束，完全由应用层控制冷却期
- **优点**: 灵活，可动态调整冷却期
- **缺点**: 可能产生脏数据，需要应用层保证一致性
- **风险评估**: 中，并发情况下可能重复插入

##### 方案C: 精确到分钟去重
- **描述**: `UNIQUE (user_id, poi_id, date_trunc('minute', checkin_time))`
- **优点**: 更精细的控制
- **缺点**: 与业务冷却期不完全对齐
- **风险评估**: 低，但可能产生 confusion

#### 决策依据
1. **业务需求匹配度** - 40%
2. **数据一致性保证** - 30%
3. **实现复杂度** - 20%
4. **性能影响** - 10%

#### 最终决策
选择方案 **A（按小时去重约束）**，理由:
- 与 API 契约中 `checkin.cooldown_seconds=3600` 完全匹配
- 数据库层保证数据一致性，减少应用层复杂性
- 业务上允许用户离开后（超过1小时）重新打卡合理
- 测试场景可通过特殊用户或测试数据绕过

#### 实施要求
- 实施团队: Backend Agent D012
- 实施时间: 今日内
- 验收标准: 约束生效，测试用户可1小时后重复打卡
- 回滚方案: 移除约束，恢复原约束

#### 后续影响
- 需要更新数据库设计文档
- App 端需适配可能的约束错误提示
- 业务规则文档需要同步更新

#### 决策回顾计划
- 回顾时间: 2026-03-24
- 回顾指标: 重复打卡投诉率 < 0.1%
- 负责人: 架构指导Agent D017

### 决策编号: DB-002
#### 决策主题
JSONB 字段与原生数组类型选择

#### 决策时间
2026-03-17

#### 决策状态
🔄 进行中（短期使用 JSONB，中期评估迁移）

#### 参与方
- 提议方: 架构指导Agent D017
- 决策方: 架构组
- 影响方: Backend, App, 前端

#### 问题背景
poems 表的 tags、best_seasons、solar_terms 等字段当前设计为 JSONB，但对于固定结构的数组数据，PostgreSQL 原生数组类型可能更高效。

#### 备选方案
##### 方案A: 保持 JSONB
- **描述**: 维持当前 JSONB 设计
- **优点**: 灵活，易于扩展，与 API JSON 格式直接对应
- **缺点**: 索引体积大，查询性能略差，需要解析开销
- **风险评估**: 低，技术成熟

##### 方案B: 迁移到原生数组
- **描述**: 改为 `TEXT[]` 数组类型
- **优点**: 查询性能更好，索引更小，与 PostgreSQL 数组操作集成
- **缺点**: 迁移成本高，需要数据转换，与 API JSON 格式需要转换
- **风险评估**: 中，数据迁移风险

##### 方案C: 混合方案
- **描述**: 新字段使用数组，旧字段保持 JSONB，逐步迁移
- **优点**: 渐进式改进，风险可控
- **缺点**: 系统复杂度增加，需要维护两种类型
- **风险评估**: 中高，维护成本增加

#### 决策依据
1. **当前阶段优先级** - 35%
2. **性能需求** - 25%
3. **开发效率** - 20%
4. **长期维护成本** - 20%

#### 最终决策
选择方案 **C（混合方案）**，分阶段实施:
- **阶段1（V1.0）**: 保持 JSONB，添加 GIN 索引，监控性能
- **阶段2（V1.1）**: 评估性能数据，如需要则创建数组字段，双写
- **阶段3（V1.2）**: 如数组性能显著提升，逐步迁移旧数据

理由:
- 当前 MVP 阶段开发效率优先
- JSONB 已能满足性能要求，通过索引优化可提升
- 为未来优化保留可能性，风险可控

#### 实施要求
- 实施团队: Backend Agent D012
- 实施时间: 阶段1今日完成，阶段2下周评估
- 验收标准: JSONB 索引创建，查询性能达标
- 回滚方案: 移除索引，恢复原状

#### 后续影响
- 需要监控 JSONB 字段查询性能
- 未来迁移需要更新数据转换逻辑
- API 层需要保持兼容性

#### 决策回顾计划
- 回顾时间: 2026-03-24（阶段1）
- 回顾指标: JSONB 查询 P95 < 50ms
- 负责人: Backend Agent D012

## 2. API 设计决策

### 决策编号: API-001
#### 决策主题
错误响应格式标准化

#### 决策时间
2026-03-17

#### 决策状态
✅ 已确定

#### 参与方
- 提议方: 架构指导Agent D017
- 决策方: 架构组
- 影响方: Backend, App, 前端

#### 问题背景
需要统一各端的错误处理，确保错误信息对用户友好且便于排查。

#### 备选方案
##### 方案A: 详细错误信息
- **描述**: 
```json
{
  "code": 40001,
  "message": "参数错误: lat 字段缺失",
  "error_detail": {
    "field": "lat",
    "reason": "required field missing",
    "validation_rule": "required"
  },
  "timestamp": 1710394800
}
```
- **优点**: 信息完整，便于前端展示和排查
- **缺点**: 响应体积稍大，可能暴露内部细节
- **风险评估**: 低

##### 方案B: 简洁错误信息
- **描述**:
```json
{
  "code": 40001,
  "message": "参数错误"
}
```
- **优点**: 响应简洁，不易暴露细节
- **缺点**: 排查困难，前端无法提供针对性提示
- **风险评估**: 中

##### 方案C: 分级错误信息
- **描述**: 生产环境返回简洁信息，开发/测试环境返回详细信息
- **优点**: 平衡安全性和可排查性
- **缺点**: 环境差异可能导致排查困难
- **风险评估**: 中

#### 决策依据
1. **开发调试效率** - 30%
2. **用户体验** - 30%
3. **安全性** - 25%
4. **实现复杂度** - 15%

#### 最终决策
选择方案 **A（详细错误信息）**，理由:
- 觅诗项目非高安全敏感系统，适当暴露细节可接受
- 便于开发调试，减少沟通成本
- 前端可根据 error_detail 提供更精准的用户提示
- 可通过日志脱敏处理敏感信息

安全补充措施:
- error_detail 中不包含敏感数据（如密码、token）
- 生产环境日志脱敏
- 监控异常错误模式

#### 实施要求
- 实施团队: Backend Agent D012
- 实施时间: 今日完成
- 验收标准: 所有错误响应符合格式，测试覆盖
- 回滚方案: 移除 error_detail 字段

#### 后续影响
- 需要更新 API 契约文档
- 各端错误处理逻辑需要适配
- 错误监控系统需要解析新格式

#### 决策回顾计划
- 回顾时间: 2026-03-20
- 回顾指标: 错误排查平均时间降低 30%
- 负责人: 架构指导Agent D017

### 决策编号: API-002
#### 决策主题
分页参数设计

#### 决策时间
2026-03-17

#### 决策状态
✅ 已确定

#### 参与方
- 提议方: API 契约设计
- 决策方: 架构组
- 影响方: Backend, App, 前端

#### 问题背景
需要统一的分页方案，支持列表接口的高效分页。

#### 备选方案
##### 方案A: limit/offset 分页
- **描述**: `?limit=20&offset=0`
- **优点**: 实现简单，支持随机跳页
- **缺点**: 大数据集 offset 性能差，数据变动时可能重复或遗漏
- **风险评估**: 低

##### 方案B: cursor 分页
- **描述**: `?limit=20&cursor=eyJpZCI6MTIzLCJ0c19kZXNjIjo...`
- **优点**: 性能好，数据变动时稳定
- **缺点**: 实现复杂，不支持随机跳页
- **风险评估**: 中

##### 方案C: 时间范围分页
- **描述**: `?limit=20&since=2026-03-01T00:00:00Z`
- **优点**: 适合时间序列数据
- **缺点**: 不适用于非时间序列数据
- **风险评估**: 低

#### 决策依据
1. **实现复杂度** - 30%
2. **性能要求** - 30%
3. **用户体验** - 25%
4. **数据特性** - 15%

#### 最终决策
选择方案 **A（limit/offset 分页）**，理由:
- 觅诗初期数据量不大，offset 性能问题不突出
- 实现简单，各端支持成本低
- 支持随机跳页，用户体验好
- 可未来升级为混合方案（cursor 优化）

性能优化措施:
- 添加合适索引支持分页查询
- limit 最大 100，默认 20
- 监控慢分页查询，适时优化

#### 实施要求
- 实施团队: Backend, App, 前端
- 实施时间: 今日完成
- 验收标准: 所有列表接口支持分页
- 回滚方案: 移除分页参数

#### 后续影响
- 数据库查询需要优化分页性能
- 前端需要实现分页组件
- API 文档需要更新分页说明

#### 决策回顾计划
- 回顾时间: 2026-03-31（数据量达到 10 万后）
- 回顾指标: 分页查询 P95 < 100ms

#### 问题背景

#### 备选方案
##### 方案A: 激进处理
- **描述**: 在 MVP 前处理所有高优先级债务
- **优点**: 代码质量高，长期维护成本低
- **缺点**: 延迟上线，短期资源紧张
- **风险评估**: 中高

##### 方案B: 保守处理
- **描述**: 仅处理阻碍功能的债务，其余延后
- **优点**: 快速上线，验证商业模式
- **缺点**: 债务累积，后期重构成本高
- **风险评估**: 中

##### 方案C: 平衡策略
- **描述**: 处理关键债务，制定明确的偿还计划
- **优点**: 平衡速度和质量，可预测的技术路线
- **缺点**: 需要持续管理和跟踪
- **风险评估**: 低

1. **业务上线紧迫性** - 40%
2. **债务影响程度** - 30%
3. **团队资源** - 20%
4. **长期成本** - 10%

#### 最终决策
选择方案 **C（平衡策略）**，具体策略:
1. **立即处理（本周）**: 阻碍功能、安全风险、严重性能问题的债务

## 6. 决策制定原则

### 6.1 决策层级
1. **架构级决策**: 影响多团队、长期技术方向，由架构组决策
2. **团队级决策**: 影响单个团队，由团队技术负责人决策
3. **实施级决策**: 具体实现细节，由开发者决策

### 6.2 决策流程
1. **问题识别**: 明确问题背景和约束
2. **方案调研**: 收集备选方案，分析优缺点
3. **风险评估**: 评估各方案风险
4. **决策会议**: 相关方讨论，形成决策
5. **文档记录**: 记录决策过程和依据
6. **实施跟踪**: 跟踪决策执行效果
7. **定期回顾**: 评估决策效果，必要时调整

### 6.3 决策质量评估指标
- **实施符合度**: 决策是否按计划实施
- **问题解决度**: 决策是否解决了原问题
- **副作用评估**: 是否有未预见的副作用
- **团队满意度**: 相关团队对决策的接受度
- **业务影响**: 对业务目标的贡献度
