## 2. 逐项技术变更评审

### 2.1 MISHI-001：数据库外键约束修复

**变更内容**：
- 修改 checkins 表的 poi_id 和 poem_id 外键约束，添加 `ON DELETE CASCADE`
- 具体 SQL（来自数据库评审报告）：
```sql
ALTER TABLE checkins 
  DROP CONSTRAINT checkins_poi_id_fkey,
  ADD CONSTRAINT checkins_poi_id_fkey 
    FOREIGN KEY (poi_id) REFERENCES pois(id) ON DELETE CASCADE;

ALTER TABLE checkins 
  DROP CONSTRAINT checkins_poem_id_fkey,
  ADD CONSTRAINT checkins_poem_id_fkey 
    FOREIGN KEY (poem_id) REFERENCES poems(id) ON DELETE CASCADE;
```

**架构影响评估**：
- **数据一致性**: 修复后，删除 POI 或诗词时，相关打卡记录将自动删除，确保参照完整性
- **服务边界**: 符合 Geo Service 和 Content Service 的数据所有权边界
- **API 影响**: 无直接影响，API 层无需变更
- **性能影响**: 轻微，级联删除可能增加删除操作的执行时间

**风险识别**：
- **风险等级**: 中风险
- **风险描述**: 如果 checkins 表存在与 poi_id/poem_id 不匹配的孤儿数据，添加约束可能失败
- **影响范围**: 数据库迁移操作
- **可能性**: 中等（取决于现有数据质量）

**架构决策**：
1. **级联策略统一原则**: 所有外键约束应统一采用 `ON DELETE CASCADE` 策略，除非有明确的业务理由采用其他策略（如 SET NULL）
2. **数据清理前置**: 执行约束修复前，必须检查并清理潜在的孤儿数据

**审核状态**: ✅ **批准执行**，但要求：
1. Backend Agent 提供数据检查脚本，验证无孤儿数据
2. 在生产环境执行前，在测试环境充分验证
3. 记录回滚方案（如何恢复原约束）

### 2.4 MISHI-004：checkins 表唯一约束调整

**变更内容**：
- 将唯一约束从 `UNIQUE (user_id, poi_id, checkin_time)` 调整为 `UNIQUE (user_id, poi_id, date_trunc('hour', checkin_time))`
- 具体 SQL：
```sql
ALTER TABLE checkins 
  DROP CONSTRAINT checkins_user_poi_time,
  ADD CONSTRAINT checkins_user_poi_hour_unique 
    UNIQUE (user_id, poi_id, date_trunc('hour', checkin_time));
```

**架构影响评估**：
- **业务规则对齐**: 调整后与 API 契约中的冷却期规则（3600秒）一致
- **数据完整性**: 仍防止同一用户在同一地点同一小时内重复打卡，满足业务需求
- **性能影响**: 轻微，索引大小略有增加（按小时截断比精确时间戳粒度更粗）
- **API 影响**: 无直接影响，API 契约中的冷却期校验仍需要在应用层实现

**风险识别**：
- **风险等级**: 中风险
- **风险描述**: 如果业务冷却期规则变化（非整小时），约束可能再次不匹配
- **影响范围**: 打卡业务逻辑，用户体验
- **可能性**: 低（业务规则相对稳定）

**架构决策**：
1. **约束与业务规则对齐原则**: 数据库约束应与核心业务规则保持一致
2. **应用层补充校验**: 数据库约束是最后防线，应用层应实现完整的业务校验
3. **约束设计灵活性**: 唯一约束应考虑业务规则可能的演变

**审核状态**: ✅ **批准执行**，但要求：
1. Backend Agent 验证调整不会影响现有合法数据
2. 在 Checkin Service 中加强冷却期校验，作为业务层保障
3. 记录约束调整的决策依据和潜在影响

## 4. 架构决策记录（ADR）更新需求

以下决策需要在 `collab/99_decisions/` 中记录：

### 4.1 ADR-001: 数据库外键约束策略
- **决策**: 所有外键约束统一采用 `ON DELETE CASCADE` 策略
- **背景**: 当前 checkins 表的外键策略不一致，存在数据完整性风险
- **选项评估**: 
  - CASCADE: 自动删除关联记录，保持参照完整性
  - SET NULL: 可能留下无意义的空值引用
  - RESTRICT: 阻止删除，需要应用层处理
- **选择理由**: CASCADE 最符合业务逻辑（删除 POI/诗词时，相关打卡记录应一并删除）
- **影响**: 需要数据清理前置，确保无孤儿数据

### 4.2 ADR-002: 客户端多环境配置管理
- **决策**: 客户端必须支持多环境配置，并通过 CI/CD 验证
- **背景**: Base URL 错误导致应用完全不可用
- **选项评估**:
  - 构建时变量: 灵活但需要多构建版本
  - 运行时配置: 单一 APK/IPA，通过配置文件切换
  - 混合方案: 构建时确定环境，运行时可有限调整
- **选择理由**: 构建时变量最安全，避免生产配置泄露到构建产物中
- **影响**: 需要调整 CI/CD 流水线，支持多环境构建

### 4.3 ADR-003: 数据库分区依赖管理
- **决策**: 关键功能的外部依赖必须有已验证的备选方案
- **背景**: pg_cron 扩展可用性不确定，影响分区功能
- **选项评估**:
  - 单一依赖: 简单但风险高
  - 备选方案: 增加复杂度但提高可用性
  - 功能降级: 无分区功能，性能下降但可用
- **选择理由**: 备选方案平衡了功能完整性和可用性
- **影响**: 需要设计和维护两套方案

### 4.4 ADR-004: 契约驱动客户端开发
- **决策**: 客户端实现必须严格遵循发布的 API 契约，建议使用代码生成
- **背景**: 模型层多处不匹配 API 契约，导致运行时错误
- **选项评估**:
  - 手动实现: 灵活但容易出错
  - 代码生成: 一致性好，契约变更自动反映
  - 混合方案: 核心模型生成，业务模型手动
- **选择理由**: 代码生成确保契约一致性，减少人为错误
- **影响**: 需要建立代码生成流水线，增加构建步骤

**执行要求**:
1. 架构师负责在今日内创建这些 ADR 文档
2. 各角色在相关工作中必须遵循 ADR 决策
3. ADR 变更需要架构评审和记录
