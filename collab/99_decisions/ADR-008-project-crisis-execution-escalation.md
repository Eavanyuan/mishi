# ADR-008: 项目危机执行升级机制

## Context
在觅诗项目危机响应过程中，发现严重的执行问题：
1. 架构师提供了完整可执行的数据库紧急方案 (09:45)
2. Backend Agent被要求09:55前执行数据安全检查并报告结果
3. 截至09:59，Backend无任何响应，无状态报告，无执行结果
4. 紧急方案执行完全失败，检查点失效
5. 项目从技术危机升级为执行危机

这暴露出严重的管理问题：
- 紧急方案无法触发有效执行
- 无响应时缺乏强制升级机制
- 责任不明确，执行无监督
- 沟通完全断裂，无法评估问题

需要建立正式的项目危机执行升级机制，确保在紧急情况下方案能够被强制执行，避免因个别角色无响应导致项目完全停滞。

## Decision
建立四级项目危机执行升级机制，明确阈值、路径和强制措施：

### 1. 执行升级阈值定义
基于紧急方案提供后的响应时间：

| 级别 | 时间阈值 | 状态 | 触发条件 |
|------|----------|------|----------|
| Level 1 | 0-15分钟 | 提醒 | 紧急方案提供后15分钟内无响应 |
| Level 2 | 15-30分钟 | 强制 | 提醒后15分钟内仍无响应 |
| Level 3 | 30-60分钟 | 介入 | 强制要求后仍无有效执行 |
| Level 4 | 60+分钟 | 重组 | 持续无响应，需资源重新分配 |

**特殊阈值**: 对于有明确检查点的任务 (如09:55)，检查点时间即为Level 2触发点。

### 2. 四级升级路径

#### Level 1: Architect提醒
- **触发**: 紧急方案提供后15分钟内无响应
- **行动**: 
  1. Architect通过正式渠道提醒责任人
  2. 明确要求响应时间和内容
  3. 记录提醒时间和内容
- **沟通**: 方案文档内添加提醒记录

#### Level 2: Coordinator强制
- **触发**: Level 1提醒后15分钟内仍无响应
- **行动**:
  1. Coordinator强制更新任务状态为`blocked` (原因: 无响应)
  2. 设置紧急检查点 (5-15分钟间隔)
  3. 通知PM准备介入
- **沟通**: 依赖队列状态更新，每日同步记录

#### Level 3: PM介入
- **触发**: Level 2强制后仍无有效执行
- **行动**:
  1. PM直接联系责任人，要求解释
  2. 评估执行障碍 (技术、资源、意愿)
  3. 制定强制执行方案
  4. 考虑任务所有权临时转移
- **沟通**: PM正式文档记录介入原因和决策

#### Level 4: 资源重新分配
- **触发**: Level 3介入后仍无法解决问题
- **行动**:
  1. 暂停原责任人相关任务
  2. 分配替代资源执行
  3. 调整项目范围和优先级
  4. 可能的技术方案降级
  5. 项目生存可行性评估
- **沟通**: 项目危机恢复计划，明确变更和影响

### 3. 强制措施库
根据危机级别可采取的强制措施:

| 措施 | 适用级别 | 内容 | 风险 |
|------|----------|------|------|
| 状态强制更新 | Level 2+ | Coordinator强制更新任务状态 | 低 |
| 检查点加密 | Level 2+ | 缩短检查间隔，增加频率 | 中 |
| 任务暂停 | Level 3+ | 暂停责任人其他任务 | 中高 |
| 所有权转移 | Level 4 | 任务转移到其他资源 | 高 |
| 技术方案降级 | Level 4 | 接受更高风险方案 | 高 |
| 范围调整 | Level 4 | 缩小项目范围 | 很高 |

### 4. 紧急沟通要求
危机执行期间必须遵守的沟通规则:

1. **状态报告频率**:
   - Level 1: 每30分钟
   - Level 2: 每15分钟  
   - Level 3: 每10分钟
   - Level 4: 每5分钟

2. **报告内容要求**:
   - 执行进展 (已完成、进行中、阻塞)
   - 具体问题 (技术、资源、其他)
   - 需要支持 (技术指导、资源、决策)
   - 下一步计划 (具体行动和时间)

3. **沟通渠道**:
   - 主要: 角色域文档 + Completion Sync
   - 紧急: Scheduling Request + 每日同步
   - 升级: PM正式文档 + 危机恢复计划

### 5. 责任与问责
明确各角色在危机执行中的责任:

| 角色 | 主要责任 | 升级责任 |
|------|----------|----------|
| **执行责任人** | 按时执行方案，报告进展和问题 | 无响应将触发升级 |
| **架构师** | 提供可行方案，技术指导，评估进展 | 触发Level 1提醒 |
| **Coordinator** | 调度资源，更新状态，监控进展 | 执行Level 2强制 |
| **PM** | 业务决策，资源协调，范围管理 | 执行Level 3-4介入 |

**问责原则**: 无响应即失职，触发升级无豁免。

## Alternatives
考虑过的其他选项：

### 1. 保持现有流程不变
- **优点**: 简单，不增加复杂度
- **缺点**: 已证明无效，导致项目危机
- **评估**: 不可接受，当前危机的直接原因

### 2. 仅增加提醒机制
- **优点**: 轻量，易于实施
- **缺点**: 无强制力，可能仍被忽略
- **评估**: 不足以保证紧急方案执行

### 3. 完全自动化升级
- **优点**: 快速，无人工延迟
- **缺点**: 缺乏灵活性，可能误判
- **评估**: 技术复杂，当前不可行

### 4. 分级升级机制 (选择方案)
- **优点**: 平衡强制力和灵活性，有明确路径
- **缺点**: 增加管理复杂度
- **评估**: 最佳平衡，可应对各种情况

## Consequences
### 正面影响
1. **保证执行**: 紧急方案有强制执行机制
2. **快速响应**: 明确的时间阈值和升级路径
3. **责任清晰**: 各角色在危机中的职责明确
4. **风险控制**: 避免因个别角色导致项目失败
5. **透明度**: 升级过程可追踪，决策可审计

### 负面影响
1. **管理复杂度**: 增加危机管理流程
2. **团队压力**: 严格的报告要求和升级威胁
3. **关系风险**: 强制措施可能影响团队关系
4. **误判风险**: 可能对合理延迟过度反应
5. **依赖管理**: 需要所有角色理解和遵守

### 缓解措施
1. **明确阈值**: 仅对P0/P1紧急任务使用
2. **沟通培训**: 确保团队理解机制目的
3. **灵活性保留**: PM有最终裁量权
4. **事后复盘**: 每次升级后总结经验优化
5. **正面激励**: 配合良好的团队获得认可

## Rollback Plan
如果需要回滚此决策：

1. **短期回滚** (机制不适应):
   - 恢复原有宽松流程
   - 接受可能再次出现执行危机
   - 加强团队自管理和责任感培养

2. **中期调整** (部分机制问题):
   - 调整时间阈值 (延长或缩短)
   - 修改升级路径步骤
   - 优化强制措施库

3. **长期优化** (文化不适应):
   - 建立更有效的团队协作文化
   - 改进任务分配和资源管理
   - 减少对强制机制的依赖

**回滚触发条件**:
- 机制被滥用，导致团队士气严重受损
- 误判频繁发生，影响正常协作
- 团队成熟度提高，可自我管理危机
- 出现更好的危机管理方案
