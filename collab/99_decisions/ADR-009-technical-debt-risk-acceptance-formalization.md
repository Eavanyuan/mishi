# ADR-009: 技术债务与风险接受正式化

## Context
在觅诗项目危机响应过程中，团队做出了多项技术降级决策：
1. 数据库外键约束从 `ON DELETE CASCADE` 降级为 `RESTRICT` 模式 (ADR-007)
2. API范围大幅缩减，延后复杂功能 (ADR-006)  
3. 季节推荐算法从动态计算降级为静态列表
4. 客户端多环境配置简化实现
5. 分区优化延后，接受性能风险

这些决策带来了明确的技术债务和业务风险，但当前处于危机响应状态，需要快速解除阻塞。然而，缺乏对这些技术债务和风险的正式记录、责任分配和偿还计划。

如果不对这些技术债务进行正式化管理，可能导致：
- 团队对已接受风险认识不一致
- 技术债务无限期积累，影响系统长期健康
- 缺乏明确的偿还责任和时间表
- 风险监控缺失，问题爆发时无预警

需要建立正式的技术债务与风险接受记录机制，确保降级决策可追踪、可管理、可偿还。

## Decision
建立正式的技术债务与风险接受管理机制，包含以下要素：

### 1. 技术债务登记册
创建 `technical-debt-registry.md` 文档，记录所有已接受的技术债务：

**登记条目格式**:
```yaml
debt_id: TD-001
title: 外键约束降级 (ON DELETE CASCADE → RESTRICT)
decision_ref: ADR-007
created_date: 2026-03-18
responsible: Backend Agent
priority: P1 (高)
estimated_impact: 中 (数据一致性风险)
repayment_plan: V2.0前恢复强一致性约束
monitoring_metric: 孤儿数据增长率 < 5%/月
status: active
```

**必填字段**:
- `debt_id`: 唯一债务标识
- `title`: 债务描述
- `decision_ref`: 相关决策文档
- `created_date`: 创建日期
- `responsible`: 责任人或团队
- `priority`: 偿还优先级 (P0-P3)
- `estimated_impact`: 预估影响 (低/中/高)
- `repayment_plan`: 偿还计划和时间
- `monitoring_metric`: 监控指标
- `status`: 状态 (active, in_repayment, repaid, cancelled)

### 2. 风险接受登记册
创建 `risk-acceptance-registry.md` 文档，记录所有已接受的业务和技术风险：

**登记条目格式**:
```yaml
risk_id: RA-001
title: 数据不一致风险 (外键约束降级)
decision_ref: ADR-007
accepted_by: PM Agent + Architect Agent
acceptance_date: 2026-03-18
risk_level: 中
business_impact: 用户可能看到不一致的数据
technical_impact: 应用层需补偿，复杂度增加
mitigation_measures: 应用层验证、定期清理、监控告警
escalation_threshold: 孤儿数据 > 1000条或每月增长 > 10%
review_schedule: 每月评审一次
status: accepted
```

**必填字段**:
- `risk_id`: 唯一风险标识
- `title`: 风险描述
- `decision_ref`: 相关决策文档
- `accepted_by`: 接受决策者
- `acceptance_date`: 接受日期
- `risk_level`: 风险等级 (低/中/高)
- `business_impact`: 业务影响
- `technical_impact`: 技术影响
- `mitigation_measures`: 缓解措施
- `escalation_threshold`: 升级阈值
- `review_schedule`: 评审计划
- `status`: 状态 (accepted, mitigated, escalated, resolved)

### 3. 偿还计划管理
为每个技术债务制定明确的偿还计划：

**偿还计划要素**:
1. **目标版本**: 计划在哪一版本解决
2. **所需资源**: 需要的人力、时间、技术资源
3. **前置条件**: 偿还前必须满足的条件
4. **成功标准**: 如何确认债务已偿还
5. **回滚计划**: 如果偿还失败怎么办

**示例**:
```yaml
repayment_plan:
  target_version: V2.0 (预计2026-06-30)
  required_resources: Backend 5人天，DBA 2人天
  prerequisites: 
    - 数据清理工具完成
    - 业务低峰期窗口
    - 用户通知完成
  success_criteria:
    - 外键约束恢复为 ON DELETE CASCADE
    - 无孤儿数据存在
    - 删除操作正常级联
  rollback_plan: 如失败，回退到 RESTRICT 模式
```

### 4. 监控与告警机制
为每个技术债务和接受风险建立监控：

**监控类型**:
1. **技术指标监控**: 数据库性能、数据一致性、错误率
2. **业务指标监控**: 用户体验、功能可用性、用户反馈
3. **趋势监控**: 债务/风险指标的增长趋势
4. **阈值告警**: 达到升级阈值时自动告警

**监控责任**:
- **技术监控**: Architect + Backend
- **业务监控**: PM + Frontend/App
- **告警响应**: Coordinator + 相关责任人

### 5. 定期评审机制
建立定期的技术债务与风险评审：

**评审频率**:
- **周度**: 检查监控指标，评估趋势
- **月度**: 全面评审债务/风险状态
- **每版本**: 评估偿还计划可行性，调整优先级

**评审参与者**:
- PM: 业务影响评估，优先级调整
- Architect: 技术可行性评估，方案设计
- 相关责任人: 执行进展报告
- Coordinator: 调度和资源协调

### 6. 版本规划集成
将技术债务偿还集成到版本规划中：

**版本规划要求**:
1. 每个版本必须包含一定比例的技术债务偿还工作
2. 高优先级债务 (P0-P1) 必须在指定版本前解决
3. 新功能开发与债务偿还平衡考虑
4. 技术债务作为版本成功标准的一部分

## Alternatives
考虑过的其他选项：

### 1. 非正式记录 (当前状态)
- **优点**: 简单，无管理开销
- **缺点**: 债务容易遗忘，风险失控，无偿还压力
- **评估**: 已导致当前危机，不可接受

### 2. 轻量级标记
- **优点**: 部分记录，管理开销小
- **缺点**: 缺乏完整性和强制性
- **评估**: 可能仍不足以保证偿还

### 3. 完整债务管理系统 (选择方案)
- **优点**: 全面管理，可追踪，可执行
- **缺点**: 管理复杂度增加，初期投入
- **评估**: 最佳平衡，确保债务不被遗忘

### 4. 外部工具集成
- **优点**: 专业化工具，功能强大
- **缺点**: 集成成本，学习曲线
- **评估**: 当前阶段过度复杂

## Consequences
### 正面影响
1. **债务透明化**: 团队清楚知道存在哪些技术债务
2. **可追踪性**: 债务创建、状态、偿还过程可追踪
3. **责任明确**: 每个债务有明确的责任人
4. **计划性**: 有明确的偿还计划和时间表
5. **风险可控**: 接受的风险有监控和告警
6. **决策支持**: 为版本规划和资源分配提供依据

### 负面影响
1. **管理开销**: 增加文档和维护工作
2. **流程复杂性**: 引入新的管理流程
3. **团队阻力**: 可能被看作额外负担
4. **执行压力**: 明确的偿还计划带来执行压力
5. **灵活性降低**: 正式流程可能降低灵活性

### 缓解措施
1. **渐进实施**: 先从高优先级债务开始，逐步完善
2. **工具简化**: 使用简单文档格式，减少工具复杂度
3. **文化引导**: 强调债务管理对项目健康的重要性
4. **灵活调整**: 允许根据实际情况调整偿还计划
5. **价值沟通**: 明确展示债务管理带来的长期价值

## Rollback Plan
如果需要回滚此决策：

1. **短期回滚** (流程不适应):
   - 恢复非正式记录方式
   - 接受技术债务可能失控的风险
   - 依靠团队自觉性和临时评审

2. **中期调整** (部分机制问题):
   - 简化登记格式，减少必填字段
   - 降低评审频率
   - 放宽监控要求

3. **长期优化** (文化不匹配):
   - 加强技术债务管理文化培养
   - 改进激励机制，奖励债务偿还
   - 寻找更适合团队的轻量级方案

**回滚触发条件**:
- 管理开销远超收益
- 团队强烈抵制，影响生产力
- 流程过于僵化，阻碍正常开发
- 出现更好的债务管理方案
