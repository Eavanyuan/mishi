# ADR-006: API 范围降级决策

## Context
在觅诗项目危机恢复过程中，发现：
1. 数据库方案严重逾期，导致后端开发完全停滞
2. 原始API契约范围过广，涉及复杂功能（动态推荐、社交打卡、路线规划等）
3. 项目面临生存危机，需要快速恢复可控进度
4. PM提出MVP重新定义，聚焦核心诗词阅读和语音体验

原始API契约 (`architecture/api_contracts_v1.yaml`) 包含7个主要端点，涵盖地理推荐、诗词详情、打卡、路线、音频、视频等完整功能。在当前技术团队能力和时间约束下，完整实现所有功能不可行。

需要调整API范围，聚焦核心价值，确保项目能在有限时间内交付可用产品。

## Decision
对API范围进行战略降级，聚焦核心功能，延后复杂功能：

### 1. 核心API (V1.0 MVP 必须实现)
| 端点 | 功能 | 实现要求 |
|------|------|----------|
| `GET /poems/{poem_id}` | 诗词详情 | 完整实现，静态数据源 |
| `GET /audio/{poem_id}` | 朗读音频 | 完整实现，预生成音频 |
| `GET /geo/nearby` | 附近点位 | 简化实现，返回预置静态点位 |

### 2. 基础API (V1.0 MVP 简化实现)
| 端点 | 功能 | 实现要求 |
|------|------|----------|
| `POST /checkins` | 打卡记录 | 基础实现，无复杂验证和社交功能 |
| `GET /checkins/history` | 打卡历史 | 基础查询，简单分页 |

### 3. 延后API (V2.0 或后续版本)
| 端点 | 功能 | 延后理由 |
|------|------|----------|
| `GET /poems/recommend` | 到地推荐 | 算法复杂，依赖地理位置和用户数据 |
| `GET /routes/{city_code}` | 旅行路线 | 业务逻辑复杂，需要路线规划和优化 |
| `POST /video/jobs` | 动画生成 | AI成本高，技术复杂度高 |
| `GET /video/jobs/{job_id}` | 任务状态 | 依赖动画生成功能 |
| `GET /profile` | 用户资料 | 社交功能非核心 |
| `POST /favorites` | 收藏功能 | 增强功能，非核心 |

### 4. API契约管理调整
1. **创建降级版契约**: `api_contracts_v1_mvp.yaml` 聚焦核心端点
2. **明确版本标识**: 在响应头中包含 `X-API-Version: mvp-v1`
3. **向后兼容考虑**: 保留原始契约结构，但标注实现状态
4. **客户端适配**: 客户端根据API版本调整功能展示

## Alternatives
考虑过的其他选项：

### 1. 保持完整API范围
- **优点**: 功能完整，用户体验好
- **缺点**: 实现周期长，当前团队能力无法按时完成
- **评估**: 已证明不可行，导致项目危机

### 2. 仅实现诗词和音频
- **优点**: 最简单，最快交付
- **缺点**: 功能过于单一，商业价值有限
- **评估**: 价值不足，需要基础地图和打卡功能支撑场景

### 3. 分阶段实现 (选择方案)
- **优点**: 平衡交付速度和功能价值
- **缺点**: 需要明确的版本规划和管理
- **评估**: 最佳平衡，可逐步增强

### 4. 外包复杂功能
- **优点**: 加速实现，专注核心
- **缺点**: 集成风险，成本增加，质量控制难
- **评估**: 当前阶段不可行，增加复杂度

## Consequences
### 正面影响
1. **快速交付**: 聚焦核心功能，可在短期内交付可用产品
2. **降低复杂度**: 减少技术挑战，提高实现成功率
3. **资源优化**: 集中团队能力在关键功能上
4. **风险控制**: 减少不确定性和依赖
5. **用户聚焦**: 提供核心诗词阅读体验，价值明确

### 负面影响
1. **功能缺失**: 用户期望的完整功能无法立即提供
2. **用户体验降级**: 缺乏智能推荐和社交功能
3. **技术债积累**: 需要后续版本补全功能
4. **市场竞争力**: 与竞品相比功能可能不足
5. **团队士气**: 可能影响团队对项目前景的信心

### 缓解措施
1. **明确沟通**: 向利益相关方说明降级原因和收益
2. **路线图透明**: 公布功能增强路线图，建立预期
3. **质量优先**: 在有限功能内提供卓越体验
4. **快速迭代**: 建立持续交付能力，尽快补充功能
5. **用户反馈**: 收集早期用户反馈，指导功能优先级

## Rollback Plan
如果需要回滚此决策：

1. **短期回滚** (MVP发布前):
   - 恢复完整API契约实现优先级
   - 重新分配资源，延长项目时间线
   - 接受项目进一步延迟的风险

2. **中期调整** (MVP发布后):
   - 根据用户反馈调整功能优先级
   - 加速V2.0开发，补全缺失功能
   - 考虑渐进增强而非一次性补全

3. **长期策略** (市场反应不佳):
   - 重新评估产品定位和市场策略
   - 考虑技术架构调整或产品转型
   - 可能需要更根本的业务模式调整

**回滚触发条件**:
- MVP发布后用户反馈极度负面
- 市场变化导致核心功能假设错误
- 团队能力大幅提升，可同时处理更多功能
- 获得额外资源，可加速开发
