# ADR-002: 客户端多环境配置管理

## Context
觅诗 Flutter 项目中发现配置错误：
- Base URL 硬编码为 `https://api.example.com/v1`，而不是正确的 `https://api.mishi.app/v1`
- 缺乏多环境（dev/staging/prod）配置支持

这导致：
1. 应用完全无法连接到正确服务器，核心功能中断
2. 测试和开发需要使用生产环境，增加风险
3. 配置变更需要代码修改和重新构建，效率低下
4. 无法安全地在不同环境中测试不同版本的 API

需要建立可靠的客户端配置管理机制，确保配置正确性和环境隔离。

## Decision
客户端必须支持多环境配置，并通过以下方式管理：

1. **构建时环境变量**:
   - 使用 Flutter 的 `--dart-define` 或环境变量在构建时注入配置
   - 不同构建变体对应不同环境（devDebug, devRelease, stagingDebug, prodRelease 等）

2. **配置集中管理**:
   - 创建 `lib/config/` 目录，存放环境配置
   - 使用 `Config` 类统一访问所有配置项
   - 配置包括：API 地址、功能开关、第三方服务密钥等

3. **CI/CD 配置验证**:
   - 在 CI/CD 流水线中验证关键配置的正确性
   - 确保生产构建不会包含开发配置
   - 配置错误导致构建失败

4. **运行时环境识别**:
   - 应用启动时记录当前环境，便于问题排查
   - 在关于页面或开发者选项中显示当前环境

## Alternatives
考虑过的其他选项：

### 1. 运行时配置文件
- **优点**: 单一 APK/IPA，通过配置文件切换环境
- **缺点**: 
  - 生产配置可能泄露给终端用户
  - 需要额外的配置文件分发机制
  - 增加应用包体积（包含所有环境配置）

### 2. 服务器下发配置
- **优点**: 配置变更无需应用更新
- **缺点**: 
  - 应用启动依赖网络请求获取配置
  - 网络不可用时无法获取配置
  - 增加服务器复杂度和安全风险

### 3. 硬编码分支判断
- **优点**: 简单直接
- **缺点**: 
  - 配置变更需要代码修改和重新发布
  - 容易出错（如忘记修改某个分支）
  - 无法防止生产代码包含调试逻辑

### 4. 混合方案（构建时+运行时）
- **优点**: 灵活性高
- **缺点**: 
  - 复杂度高，难以维护
  - 安全边界模糊（运行时可能覆盖安全设置）

## Consequences
### 正面影响
1. **配置正确性**: 减少配置错误导致的运行时问题
2. **环境隔离**: 安全地在不同环境测试和开发
3. **构建自动化**: CI/CD 流水线可以自动构建各环境版本
4. **问题排查**: 明确知道问题发生的环境
5. **安全**: 生产配置不会泄露到构建产物中

### 负面影响
1. **构建复杂度**: 需要管理多个构建变体
2. **测试覆盖**: 需要测试所有环境变体
3. **包管理**: 需要管理多个环境的应用包
4. **开发者体验**: 本地开发需要切换环境配置

### 缓解措施
1. **脚本自动化**: 提供脚本简化环境切换和构建
2. **文档**: 详细的环境配置和构建文档
3. **默认安全**: 默认使用安全配置，避免泄露敏感信息
4. **配置验证**: 应用启动时验证配置完整性

## Rollback Plan
如果需要回滚此决策：

1. **短期回滚**（在实施前）:
   - 继续使用硬编码配置
   - 手动修改配置并重新构建

2. **中期回滚**（实施后但影响有限）:
   - 移除多环境配置代码，回归硬编码
   - 更新 CI/CD 流水线，移除配置验证
   - 需要通知开发者变更构建方式

3. **长期回滚**（已依赖多环境功能）:
   - 评估业务对多环境的需求
   - 如果必须保留多环境，可简化实现（如减少环境数量）
   - 提供迁移指南，帮助团队适应变更

**回滚触发条件**:
- 多环境配置导致构建过程过于复杂
- 团队无法有效管理多个环境版本
- 配置验证导致合法构建失败
- 安全事件（如生产配置泄露）
