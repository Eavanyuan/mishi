# ADR-004: 契约驱动客户端开发

## Context
在评审 Flutter 客户端实现时发现多处与 API 契约不匹配：
1. 模型字段命名不一致（如 API 使用 `poem_id`，客户端使用 `id`）
2. 数据结构不完整（如缺少 `score_breakdown`、`related_poi` 等嵌套对象）
3. 服务层参数名不匹配（如 API 使用 `lat`，客户端使用 `latitude`）
4. 错误处理模型不一致

这导致：
- 运行时解析错误，功能异常
- 需要额外的手工映射代码，容易出错
- API 契约变更时，客户端更新容易遗漏
- 测试覆盖率低，难以发现契约不一致问题

需要建立严格的契约驱动开发流程，确保客户端与服务器 API 的一致性。

## Decision
客户端实现必须严格遵循发布的 API 契约，并采用以下实践：

1. **代码生成优先**:
   - 使用 OpenAPI 规范 (`api_contracts_v1.yaml`) 自动生成模型类
   - 生成的服务层代码确保参数和响应类型与契约一致
   - 优先使用成熟的代码生成工具（如 `openapi-generator`、`dio` 插件等）

2. **契约即单一点源**:
   - API 契约文件 (`architecture/api_contracts_v1.yaml`) 是客户端模型的唯一来源
   - 禁止手动编写与契约对应的模型类
   - 契约变更必须通过架构评审，并更新版本号

3. **一致性验证**:
   - CI/CD 流水线中集成契约一致性检查
   - 构建时验证生成的代码与契约的同步状态
   - 运行契约测试，验证客户端与模拟服务器的交互

4. **版本管理**:
   - 客户端明确声明支持的 API 版本
   - 支持有限的后向兼容（如忽略未知字段，但记录警告）
   - 不兼容的变更需要客户端版本升级和迁移计划

## Alternatives
考虑过的其他选项：

### 1. 手动实现模型
- **优点**: 完全控制，可优化特定场景
- **缺点**: 
  - 容易出错，难以保证与契约一致
  - 契约变更时需要手动更新多处代码
  - 缺乏自动化验证手段

### 2. 运行时动态模型
- **优点**: 灵活，适应契约变更
- **缺点**: 
  - 类型不安全，IDE 支持差
  - 性能开销（运行时反射）
  - 调试困难，错误发现晚

### 3. 混合方案（核心生成，业务手动）
- **优点**: 平衡控制力和一致性
- **缺点**: 
  - 边界模糊，容易越界
  - 仍然需要手动维护部分模型
  - 可能造成代码风格不一致

### 4. 契约测试替代生成
- **优点**: 发现不一致问题，但不强制生成
- **缺点**: 
  - 发现问题时已晚（编写代码后）
  - 不防止不一致代码被提交
  - 测试维护成本高

## Consequences
### 正面影响
1. **一致性保证**: 客户端与服务器 API 完全一致
2. **开发效率**: 契约变更自动反映到客户端代码
3. **质量提升**: 减少运行时解析错误
4. **协作改善**: 明确契约作为前后端协作接口
5. **文档准确**: 生成的代码包含契约中的文档信息

### 负面影响
1. **构建复杂度**: 增加代码生成步骤
2. **生成代码控制力**: 生成代码可能不符合团队编码风格
3. **学习曲线**: 团队需要学习代码生成工具和流程
4. **工具依赖**: 依赖外部工具的质量和维护

### 缓解措施
1. **定制生成模板**: 调整生成器模板以符合团队编码规范
2. **渐进采用**: 先从核心模型开始生成，逐步扩大范围
3. **工具标准化**: 选择成熟、维护良好的工具
4. **文档和培训**: 提供代码生成流程的详细文档和示例

## Rollback Plan
如果需要回滚此决策：

1. **短期回滚**（在实施前）:
   - 继续手动实现模型
   - 加强代码审查和契约测试

2. **中期回滚**（实施后但影响有限）:
   - 停止使用代码生成，手动替换生成的模型
   - 移除生成步骤和相关配置
   - 需要重写受影响的服务层代码

3. **长期回滚**（已广泛使用生成代码）:
   - 评估生成代码的实际问题和维护成本
   - 如果决定回滚，制定迁移计划，逐步替换生成代码
   - 保留生成能力用于参考，但不作为主要开发方式

**回滚触发条件**:
- 代码生成工具存在严重缺陷或停止维护
- 生成代码导致无法解决的性能问题
- 团队无法适应生成代码的开发模式
- 契约变更频率极低，生成价值不高
