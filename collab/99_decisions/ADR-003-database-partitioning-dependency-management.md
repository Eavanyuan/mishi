# ADR-003: 数据库分区依赖管理

## Context
觅诗项目数据库设计使用分区策略处理数据增长：
- `user_events` 表设计为按月分区
- 分区维护依赖 PostgreSQL 的 `pg_cron` 扩展自动创建新分区

发现的风险：
1. `pg_cron` 扩展可能未在 PostgreSQL 实例中安装
2. 缺乏备选方案，如果扩展不可用，分区功能将失效
3. 分区维护脚本缺少错误处理和监控

这导致：
- 分区表可能无法自动创建，导致单表过大性能下降
- 数据清理和归档功能不可用
- 系统可扩展性风险

需要建立可靠的分区依赖管理策略，确保关键功能不因单一依赖失效而中断。

## Decision
对于关键功能的外部依赖，必须有以下保障措施：

1. **主方案验证**:
   - 在新环境部署时，必须验证 `pg_cron` 扩展的可用性
   - 如果不可用，优先安装扩展（需评估运维可行性和成本）

2. **备选方案准备**:
   - 准备系统级 crontab 作为备选方案
   - 备选方案必须经过测试，确保功能等价性
   - 文档化切换步骤和验证方法

3. **功能降级策略**:
   - 如果两种方案都不可用，系统应能继续运行（无分区）
   - 但需监控单表大小，达到阈值时发出告警
   - 提供手动分区创建和维护工具

4. **运维监控**:
   - 监控分区创建任务的执行状态
   - 记录分区创建失败日志并告警
   - 定期检查分区表的大小和数量

## Alternatives
考虑过的其他选项：

### 1. 单一依赖（仅 pg_cron）
- **优点**: 实现简单，依赖 PostgreSQL 原生功能
- **缺点**: 
  - 单点故障风险高
  - 某些云服务商可能不支持或限制扩展安装
  - 无法应对扩展安装失败的情况

### 2. 外部调度器（如 Kubernetes CronJob）
- **优点**: 与基础设施集成，监控和运维成熟
- **缺点**: 
  - 需要额外的权限和配置
  - 增加系统复杂度（需要访问数据库的网络和凭证）
  - 可能引入网络延迟和故障点

### 3. 应用层调度
- **优点**: 完全控制，与业务逻辑集成
- **缺点**: 
  - 增加应用层复杂度
  - 需要处理分布式环境下的任务协调
  - 可能与应用重启/扩缩容冲突

### 4. 无分区设计
- **优点**: 无依赖，简单可靠
- **缺点**: 
  - 无法应对数据增长，性能随时间下降
  - 数据清理困难，存储成本高
  - 不符合架构设计的可扩展性目标

## Consequences
### 正面影响
1. **高可用性**: 主方案失败时可切换到备选方案，保障功能连续性
2. **运维灵活性**: 适应不同的部署环境（云服务商、自建等）
3. **风险可控**: 明确的风险缓解措施和监控
4. **架构韧性**: 系统对单个组件故障的容忍度提高

### 负面影响
1. **实现复杂度**: 需要设计和维护两套方案
2. **测试负担**: 需要测试主方案和备选方案
3. **运维知识**: 团队需要掌握两种方案的运维技能
4. **切换风险**: 方案切换可能引入新问题

### 缓解措施
1. **自动化切换**: 提供脚本自动化检测和切换
2. **定期演练**: 定期测试备选方案，确保其可用性
3. **文档完善**: 详细记录两种方案的操作步骤和故障排除
4. **容量规划**: 即使无分区，也能通过其他方式（如分库分表）应对数据增长

## Rollback Plan
如果需要回滚此决策：

1. **短期回滚**（在实施前）:
   - 仅依赖 pg_cron 扩展，接受单点故障风险
   - 加强扩展安装的文档和验证

2. **中期回滚**（实施后但影响有限）:
   - 移除备选方案代码和配置
   - 简化分区维护逻辑
   - 需要评估当前环境的扩展可用性风险

3. **长期回滚**（已依赖备选方案）:
   - 如果备选方案已成为主要方案，评估是否继续需要主方案
   - 如果决定放弃主方案，移除相关代码和依赖
   - 更新监控和告警，聚焦于实际使用的方案

**回滚触发条件**:
- 备选方案维护成本过高
- 两种方案都不可靠，需要第三方案
- 业务数据量远低于预期，分区不再必要
- 架构变更（如迁移到支持分区的云数据库服务）
