# ADR-007: 数据完整性风险接受决策

## Context
在觅诗项目数据库危机应对中，面临外键约束实现难题：
1. 数据库外键约束修复方案逾期 18+ 小时
2. Backend Agent 无法按时提供完整方案
3. 项目关键路径完全阻塞，面临生存危机
4. 需要紧急方案解除阻塞，但完整的外键约束实现（ON DELETE CASCADE）涉及复杂数据迁移和验证

技术约束：
- 现有数据可能存在孤儿记录（poi_id 或 poem_id 不匹配的记录）
- 添加级联删除约束可能导致现有删除操作失败
- 完整的数据清理和迁移需要时间和详细分析
- 项目无法承受进一步延迟

需要在数据完整性风险和项目进度风险之间做出权衡决策。

## Decision
接受临时的数据完整性风险，采用降级技术方案：

### 1. 外键约束降级策略
**从**: `ON DELETE CASCADE` (自动级联删除，保证强一致性)  
**改为**: `FOREIGN KEY ... REFERENCES ...` (无级联，RESTRICT 模式)  
**理由**: 
- 避免因孤儿数据导致约束添加失败
- 简化实施复杂度，快速解除阻塞
- 删除操作仍被约束保护（防止新孤儿数据）
- 级联删除逻辑移到应用层实现

### 2. 接受的数据风险
明确接受以下风险，并制定缓解措施：

| 风险项 | 风险等级 | 接受理由 | 缓解措施 |
|--------|----------|----------|----------|
| 孤儿数据继续存在 | 中 | 不影响核心功能，只读操作正常 | 定期清理任务，监控告警 |
| 删除操作需要应用层处理 | 中 | V1.0 删除场景有限 | 软删除替代，异步清理 |
| 数据不一致可能 | 中 | 核心业务逻辑可容忍 | 应用层数据校验 |
| 引用完整性依赖应用层 | 中 | 简化数据库复杂度 | 明确的业务层验证规则 |

### 3. 应用层补偿机制
为弥补数据库约束降级，在应用层实现：

1. **软删除模式**:
   - 标记删除而非物理删除
   - 定期异步清理标记删除的数据
   - 避免外键约束冲突

2. **业务层验证**:
   - 写入时检查引用是否存在
   - 读取时处理可能的孤儿数据
   - 事务性保证关键操作一致性

3. **监控和告警**:
   - 监控孤儿数据增长
   - 监控删除失败情况
   - 定期数据一致性检查

4. **数据迁移计划**:
   - V1.0 后实施完整数据清理
   - V2.0 前恢复强一致性约束
   - 分阶段数据质量提升

### 4. 实施时间线
- **V1.0 (当前)**: 接受风险，实施降级方案
- **V1.1 (1个月后)**: 实施数据清理，减少孤儿数据
- **V1.2 (2个月后)**: 评估恢复强约束的可行性
- **V2.0 (3个月后)**: 恢复完整的数据完整性保证

### 5. 成功标准
降级方案的成功标准：
1. ✅ 数据库约束修复任务完成，阻塞解除
2. ✅ 核心业务功能正常运作
3. ✅ 数据不一致问题可控，不影响用户体验
4. ✅ 有明确的改进路线图和监控

## Alternatives
考虑过的其他选项：

### 1. 坚持完整约束方案
- **优点**: 数据完整性100%保证
- **缺点**: 项目进一步延迟，可能失败
- **评估**: 不可接受，已导致18小时阻塞

### 2. 完全移除外键约束
- **优点**: 最简单，无约束问题
- **缺点**: 数据完整性无保障，可能产生严重不一致
- **评估**: 风险过高，可能影响核心功能

### 3. 应用层完全模拟约束 (选择方案)
- **优点**: 平衡进度和完整性
- **缺点**: 应用层复杂度增加
- **评估**: 最佳平衡，可控风险

### 4. 数据大清洗后添加约束
- **优点**: 一次性解决根本问题
- **缺点**: 需要停机和详细分析，时间不确定
- **评估**: 当前不可行，缺乏时间和资源

## Consequences
### 正面影响
1. **快速解阻塞**: 可在几小时内解除项目关键路径阻塞
2. **进度恢复**: 项目恢复可控状态，避免失败风险
3. **技术简化**: 数据库层面简化，减少运维复杂度
4. **灵活处理**: 应用层可更灵活处理边缘情况
5. **渐进改进**: 可逐步提升数据质量，不影响进度

### 负面影响
1. **数据质量风险**: 可能存在不一致数据，需要额外处理
2. **应用层复杂度**: 需要实现补偿逻辑，增加代码复杂度
3. **技术债积累**: 需要后续版本偿还数据完整性债务
4. **运维负担**: 需要监控数据质量，定期清理
5. **团队认知**: 需要团队理解并接受这种权衡

### 缓解措施
1. **明确记录**: 详细记录接受的风险和缓解措施
2. **严格监控**: 建立数据质量监控体系
3. **定期清理**: 计划数据清理任务，逐步改善
4. **团队培训**: 确保团队理解数据层设计决策
5. **用户沟通**: 如有必要，向用户说明数据可靠性水平

## Rollback Plan
如果需要回滚此决策：

1. **立即回滚** (实施过程中发现问题):
   - 撤销外键约束更改
   - 恢复原始数据库状态
   - 接受项目进一步延迟
   - 寻求替代技术方案

2. **短期回滚** (V1.0发布前):
   - 实施数据大清洗
   - 添加完整外键约束
   - 更新应用层代码处理约束
   - 需要额外2-3天时间

3. **长期回滚** (V1.0发布后):
   - 制定数据迁移计划
   - 分阶段清理数据并添加约束
   - 可能需要版本过渡期
   - 用户可能感知数据变化

**回滚触发条件**:
- 数据不一致导致严重功能问题
- 应用层补偿逻辑过于复杂且不可维护
- 团队获得额外资源，可处理完整方案
- 用户对数据可靠性投诉达到不可接受水平
- 监管或合规要求强制数据完整性级别
